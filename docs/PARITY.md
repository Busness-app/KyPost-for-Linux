# Android ↔ Linux parity matrix

**Status: authoritative.** This file, not `Linux_QT_Client_Plan.md`, is the
acceptance checklist for parity work. The plan document predates several
locked decisions and still describes a dual-Qt/Ubuntu-Touch target; where the
two disagree, this file and `AGENTS.md` win.

The Android behaviour contract is `~/busness.app/kypost-android/app/AGENTS.md`.
The wire contract is the backend Go source
(`~/busness.app/kypost-server/backend/internal/api/`), never a guess.

## How to read a row

| Status | Meaning |
| --- | --- |
| **Matched** | Linux does the same thing, and a test pins it. |
| **Equivalent** | Different mechanism, same user-visible outcome. The mechanism is named. |
| **Missing** | Android has it, Linux does not, and it is agreed that Linux should. |
| **Intentional difference** | Android has it, Linux deliberately does not. A reason is required, not a shrug. |
| **Blocked** | Waiting on the backend or on a platform capability. |

A row may not sit at **Missing** without an owner phase. A row may not sit at
**Intentional difference** without a reason someone could argue with.

## 1. Mail

| Capability | Status | Notes |
| --- | --- | --- |
| Inbox, keyword tabs, folder list | Matched | |
| Delta/cursor sync | Matched | Fixed 2026-08-22. `since` is always sent; `since=0` is the full window. See `AGENTS.md` §4 — the previous two versions of that entry were both wrong. |
| Cursor scoped per (subscriber, folder) | Matched | `CursorStore::mailCursor(subscriberId, folder)`, mirroring Android's `MailCheckpoint`. |
| Full-window prune of vanished rows | Matched | `replaceFolderSnapshot` on the `delta:false` branch. |
| Cursor withheld when the cache write fails | **Better than Android** | `MailRepositoryOutcome::CacheWriteFailed`. Advancing past unwritten rows makes them unrequestable forever; Android does not check this. |
| Same message ID in two folders | Matched | PK is `(folder, message_id)` since migration 006. |
| Archive / spam / delete / move / read | Matched | |
| Reply, Reply All, Forward | Matched | Verified line-for-line against `EmailDetailActivity.kt:210`: sender + To + Cc, deduped, blanks dropped. **Neither client removes the local identity** — a 2026-08-22 review claimed Android did; it does not. |
| Drafts, attachments, HTML/plain/markup compose | Matched | |
| Open mail from a notification | Matched | The UnifiedPush envelope carries no mailbox (`PushPayloadParser.h`), so an ID cached in two folders is genuinely ambiguous. `findCachedEmail` refuses rather than opening the wrong copy. The UI still renders that as a blank page — marked `ponytail:` in `MailController::findByMessageId`. Completed 2026-08-23. The ambiguous case is no longer a blank page: an id cached in more than one mailbox is reported as its own outcome (`notificationEmailAmbiguous`) and both roots answer it with a folder chooser. No request is made for it -- a delta cannot remove an ambiguity already in the cache, so a round trip would only be a slower way to ask the same question. The dialog picks nothing by default, on cancel included: every option is a real message and guessing is the wrong-message bug the refusal exists to prevent. |
| Refresh before opening from a notification | Matched | Added 2026-08-22. `MailController::openFromNotification()` answers from the cache when the message is already there, and otherwise selects the Inbox, refreshes, and answers when that lands — so the common case (a push arrives up to 90 s before the sync that would fetch it) no longer opens a blank detail page. A **delta** refresh, not a forced full resync: the relay's cursor protocol returns everything after the stored cursor, and a message that has just arrived is by definition after it, so a full resync would re-download every body to learn the same thing. When the message still cannot be found — filed elsewhere by a server-side rule, or deleted from another client — the roots open nothing and `lastError` says why. |
| Per-route response size limits | Matched | Added 2026-08-22. `HttpClient` enforces a ceiling on both the declared `Content-Length` (at the headers, before any body arrives) and the running byte count (the only guard a chunked response leaves), reporting `NetworkError::ResponseTooLarge` and discarding the partial body. Shape follows Android's `MemoryBudget.kt`; **values deliberately differ** — Android asks the relay for `limit=50`, this client sends no limit and gets the server default of 500 with untruncated bodies, so Android's 8 MB would have broken first sync here. Default 8 MB, inbox 64 MB, attachment 25 MB. |
| Inbox window size | **Open question** | Linux sends no `limit`, so the relay's default 500 applies and a full window carries 500 untruncated HTML bodies — the largest allocation in the app, and why the response ceiling for that one route is 64 MB. Android asks for 50. Lowering it would shrink the response ~10x and allow a much tighter cap, but `replaceFolderSnapshot` prunes to the window, so it would also cut the local archive 10x. That is a product call, not a CI or security one. |
| Pull-to-refresh on mobile | **Equivalent** | Explicit refresh control. Revisit if that is judged insufficient. |

## 3. Pairing, credentials, recovery

| Capability | Status | Notes |
| --- | --- | --- |
| Pairing, TLS TOFU pinning, credential sealing, deregistration | Matched | TOFU only. The **server-published `pin=` is not honoured** — `PairingController.cpp:141-144` reads `sub`, `srv`, `pt`, `reg` and stops, so the registration POST that carries the pairing token and the push credentials still goes out inside a trust-on-first-use window. Android honours it. Tracked in `kypost-server/docs/PLATFORM_BASELINE.md` §9. |
| Non-destructive "Reconnect to server" | Matched | Added 2026-08-22, as `reconnectToServer()`. Note the review's premise was partly wrong: `removePairing()` never called `LocalDataWipe`, so cached mail and contacts already survived unpairing. What unpair actually costs is a server-side deregistration and a fresh pairing link. |
| Staged account replacement (register, then purge) | Matched | Added 2026-08-22. Pairing a **different** account now erases the previous one's cached data — and only after the replacement registration has succeeded, so a failed pairing cannot delete a working account's mail. If the purge leaves anything behind, the new pairing is refused and the device is wiped: no table carries a subscriber column, so survivors are readable by whoever pairs next. Mirrors Android's `PushSyncCoordinator.attemptPairing`. |
| Serialised registration / re-registration / pull | **Partial** | `reconnectToServer()` and `pairFromParsedParams()` guard on `m_inNetworkCall`, so no two registrations overlap, and the previous account is captured **before** the request rather than re-read after it (the TOCTOU Android's `registrationGate` closes by reading inside the mutex). Registration is still not *serialised* against an in-flight pull. As of 2026-08-22 it no longer needs to be for the mail and push paths, which discard a reply the current pairing did not authorise (row below) instead of blocking the request that produced it. Audited 2026-08-23 rather than assumed: every repository that writes account-scoped data through a DAO carries such a guard, and the two that carry none persist nothing. The audit found one site that did not — `PgpQrController` kept the previous account's key-exchange QR on screen, so a correspondent scanning it would have exchanged keys with the account this device had just removed. Fixed. |
| Replies discarded when they outlive their pairing | Matched | Added 2026-08-22. `PairingStore::stillCurrent()` compares the (subscriberId, deviceId) identity captured **before** a request against the one held when its reply lands. Enforced at every place a relay reply reaches local storage: `MailRepository::applyRefresh`, `PushRepository::pullOnce`, `FolderRepository::applyList`/`applyMutation`, `GroupsRepository::applyRefresh`, `ContactSyncRepository::applySync`, `ContactPhotoRepository::photoPathFor`, attachment downloads, and the cached PGP compose state and recipient preflight. Deliberately not keyed on `deviceSecret`, which the credential gate rewrites on every lock/unlock. Not enforced on `MailController::finishAction`, which touches only the in-memory list and writes nothing to disk. |
| Secure-store *unreadable* distinguished from *absent* | Matched | Closed 2026-08-22. `SecureStore::read()` already existed and `AppLockStore` already used it; `PairingStore::loadChecked()` now completes it for the one remaining key that decides a security question — `sub`, which decides paired-vs-not. `PairingController` refuses to register when the store cannot be read rather than treating it as "first pairing on this device". Measured, not assumed: that case was **already** refused before the request, by `credentialGateEnabled()` failing closed and `beginPair()` being unable to reseal — so there was no live leak. What changed is that the refusal now names the keyring instead of saying "Unlock KyPost first" to someone with no lock, and the protection is stated rather than emergent. `load()` keeps its `std::optional` signature for the many callers where the distinction does not matter. **Completed 2026-08-24**: `sub` was the only field that had been converted, and the other seven still went through `get()`, which turns "could not consult the store" into an empty string. A Secret Service that answered the first request and failed on the certificate pin loaded a pairing with **no TLS pin** and no TOFU enforcement, cached for the rest of the session. Every field now uses `read()`; any `Failed` fails the whole load and nothing is cached. See `AGENTS.md` §6i. |
| Certificate-renewal recovery UI | Matched | Added 2026-08-22. `Pairing.reconnectToServer()` re-anchors the pin via a forced re-registration — **not** a pin clear: the pin is only ever captured during registration, so clearing it alone would leave the device permanently unpinned. `CertificateChangeDialog.qml` shows the pinned and presented SPKI fingerprints side by side before the user decides. Non-destructive: no deregistration, no cache loss; `removePairing()` stays the destructive path. |
| Secret Service calls always terminate | Matched | Fixed 2026-08-22. `SecureStoreKeychain::runBlocking` waited on `QKeychain::Job::finished` alone, and QKeychain never emits it when its D-Bus call gives up — so the app hung **forever** at startup, before any window, with nothing in the journal. Bounded now, and a timeout maps to `Failed`, never `Absent`. Measured floor: the first call costs ~25 s inside a synchronous D-Bus call (Qt's default), which no timer can shorten; `main()`'s canary therefore stops at the first failure instead of paying it three times. |
| Sync cursors erased on wipe | Matched | Fixed 2026-08-22. `cursors.ini` survived every wipe path — `CursorStore::reset()` had no caller anywhere in the app. |

## 4. Local data protection

| Capability | Status | Notes |
| --- | --- | --- |
| PIN lock, lockout, wipe, hidden notifications | Matched | |
| Hostile Location Protection (memory-only database) | **Better than Android** | No Android equivalent. Hardened 2026-08-24: the erase now happens **before** the relaunch and the mode is refused if it fails. Previously the failure was logged and discarded, so the replacement process came up memory-only, displayed the protection as on, and left the mail it was meant to have destroyed on the disk. On failure the setting reverts and the wipe-incomplete banner is raised — deliberately not through `WipeTripwire`, whose recovery calls `wipeEverything()` and would turn a failed transition into an unpaired device. |
| Encrypted database at rest | Matched | Completed 2026-08-22. New profiles are created encrypted; existing plaintext profiles are converted automatically on the next launch (user's call — an opt-in would leave most mail in plaintext indefinitely, since most people never open Settings). The key is 32 random bytes in the secret store; `DatabaseKeyStore` reports Unreadable and Corrupt separately from Absent, because minting a replacement over a real key makes the database unopenable forever. Conversion writes a separate file, verifies it table by table against the original, swaps, re-opens in place, and only then securely deletes the plaintext — with a marker armed beforehand so an interrupted run is repaired on the following launch. Where SQLCipher is present but no key can be stored, a **new** profile runs in memory rather than writing plaintext; an **existing** one is opened as it stands, because refusing would not un-write what is already there. Both states are on the status banner. |
| Configurable background-lock grace period | Matched | Added 2026-08-22. At once / 15 s / 1 min / 5 min, defaulting to **at once** — the behaviour before the setting existed, so a grace period is only ever something a user asks for. Stored in `AppLockStore` (not `SettingsStore`: a grace period in a plain text file could be stretched by anyone with file access, who then only has to wait for the owner to walk away) and changing it requires the PIN. A grace of 0 locks **synchronously**, not through a zero-delay timer, which would leave the app unlocked for the rest of the event-loop pass. `lockNow()` — the explicit action — always locks at once and cancels any grace already running. |
| Configurable erase-after threshold, incl. "never" | Matched | Added 2026-08-22. Never / 5 / 10 / 20, defaulting to 10 (today's behaviour), stored in `AppLockStore` — **not** `SettingsStore`, which is a plain text file anyone with file access could edit to switch the erase off. Changing it requires the current PIN through the same rate-limited path as disabling the lock, and values are clamped both on write and on read. The key point: the wipe threshold and the per-process refusal floor used to be one constant, and are now separate. Choosing "never" declines the **erase** only — repeated failures are still slowed and eventually refused, which is the one limit a forward clock change cannot defeat. `clear()` resets the threshold to the default, so a "never" choice cannot survive silently into the next person's setup. |
| Interrupted-wipe tripwire, incomplete-wipe state | Matched | Added 2026-08-22. `WipeTripwire` records that a wipe STARTED, before the first byte is erased, and is cleared only by a wipe that reported every component gone. `TrackedWipe` owns the arm → wipe → disarm sequence and the startup recovery, out of `main()` where it had no seam a test could reach. A marker found at launch re-runs the wipe **before** `AppLockManager` reads the lock state; if it still cannot finish, `AppLock.wipeIncomplete` drives a `StatusBanner` row, because the one thing worse than a failed wipe is a user who thinks it succeeded. Scoped to the full erase (`wipeEverything`); Hostile Location Protection's `wipeOnDiskDataOnly` is not tracked. |
| Biometric unlock | **Intentional difference** | No portable Linux equivalent. `AGENTS.md` §4. |
| Window-content protection (`FLAG_SECURE`) | **Intentional difference** | No Wayland analogue. `AGENTS.md` §4. |

## 5. Push

| Capability | Status | Notes |
| --- | --- | --- |
| UnifiedPush with 90 s polling fallback | Matched | |
| MFA over push | **Non-goal** | Settled 2026-08-23 by the user: Linux cannot do MFA push. The relay excludes it deliberately rather than by oversight -- an MFA challenge carries sign-in metadata (IP address, user agent, the match digits), and UnifiedPush delivers through an unencrypted public broker such as ntfy.sh, so `MFATransportEligible` refuses that transport and `normalizeNativeTransport` maps platform `linux` onto it. Those devices stay fully usable for mail notifications. The row previously read **Blocked** and said to confirm the filter was gone before building any MFA UI, which described a privacy control as a temporary obstacle. What would have to change is encryption of the push payload itself, in the UnifiedPush ecosystem rather than in KyPost. `MfaController`/`MfaResponseClient` remain in the tree and are dead -- see `AGENTS.md` §4. |

## 6. OpenPGP

| Capability | Status | Notes |
| --- | --- | --- |
| Public-key QR exchange, encrypted-message awareness | Matched | |
| Client-side decryption | Matched | Completed 2026-08-23. A client-protected message carries no body, so the ciphertext is fetched on demand from `GET /api/mail/pgp-payload` (`PgpPayloadClient`), decrypted through the user's own `gpg-agent` via GPGME (`OpenPgpDecryptor`), and its MIME parsed into html/plain (`MimeBodyReader`). This client holds no key material and never sees a passphrase, so hardware tokens and smartcards work with no code; the Flatpak grants `--socket=gpg-agent`, verified present along with `gpg` and `libgpgme.so.45` in the 6.11 runtime we target. **The decrypted message is never written to the database** -- the sender chose end-to-end encryption and the database key is in the platform secret store, not behind their OpenPGP passphrase, so caching it would demote the message to the protection level of every other mail; enforced by a test that scans every column of every table. It is dropped when the reader moves on and when the app locks. Decryption is manual, not automatic on open: it prompts pinentry, which for a hardware token means physically touching the key. Nine outcomes, one sentence each, and only a transport failure offers Retry. Webmail stays offered throughout -- a key kept on another machine is an ordinary setup that decrypting here cannot help. Signatures ARE verified (2026-08-23), and the verdict is bound to the address the relay RESOLVED from the From header -- never the display form, which this client does not parse at all, because the two are attacker-separable. Four outcomes rather than a badge: signed by this sender, signed by a key nobody binds to this sender, invalid, and could-not-check. The second is the one that matters -- gpg verifies a known contact's signature on a message claiming to be from somebody else perfectly well, so a client trusting gpg's verdict alone would show a pass. Unsigned messages say nothing, rather than printing a reassuring-looking 'not signed' beside every one of them. |
| Client-side signing and encryption on send | Matched | Completed 2026-08-23. A client-custody account on a machine with a usable gpg now sends from the app: the account's own address comes from `/api/pgp/bootstrap` (`suggestedUserIDs[0]`, the same IMAP username the relay authorises the From against), recipient keys come from the relay's discovery ladder and are imported into the user's own GnuPG keyring (AGENTS.md 4b) after checking the fingerprint gpg computes against the one the relay claimed -- in a scratch keyring, so a mismatch never touches the real one. That check was completed 2026-08-24: `gpgme_op_import()` imports every key in the blob and reports them as a linked list, and only the head of it was being read — so a relay could return the expected key followed by keys of its own choosing and the whole bundle entered the real keyring. The full status list is now walked and anything other than one primary fingerprint is refused, compared by fingerprint rather than by counting entries. Signing and encryption are one `gpgme_op_encrypt_sign`, RFC 3156 combined mode. To+Cc share one delivery and each Bcc recipient gets their own, so no blind recipient is named in another's key IDs. The real subject travels only as a protected header inside the ciphertext. The Sent copy is encrypted to the sender or **not saved at all** -- a cleartext copy would land on the account's IMAP host, which holds no key. Nothing is sent if any recipient lacks a usable key, and the user is told which one; there is no downgrade to plaintext, because the relay's own fallback works by storing the message on the relay. The webmail hand-off stays for accounts this machine cannot encrypt for. Attachments travel INSIDE the encrypted part, so their filenames and bytes are encrypted with the message -- for mail somebody chose to encrypt, the filename is often the most telling thing about it. The limit that bites is not the attachment's own: the request carries one full copy per delivery and each blind-copied recipient gets their own, so this client measures the real serialized request against the relay's cap before sending and names both levers -- an attachment or some recipients. Verified against the relay's own code, not only against a reading of it: `scripts/verify-pgp-against-relay.sh` decodes a real request into the server's own `clientEncryptedSendRequest`, runs its per-delivery validation and its Sent-copy logic, and checks a non-ASCII protected subject round-trips. Proven to discriminate -- the real subject on the envelope, a cleared `sentCopyEncrypted`, and an unauthorised `From` are each rejected in the server's own words. **Not a substitute for a live relay**: nothing there proves SMTP delivery, IMAP APPEND, or that the deployed server is this version. |
| In-app private-key custody and enrolment | **Non-goal** | Decided 2026-08-22 in favour of delegating to `gpg-agent`. `AGENTS.md` §4a records the reasoning and the two accepted costs: a working GnuPG is required, and the Flatpak needs the agent socket. |

| Desktop, mobile, wide/master-detail layouts | Matched | |
| Compose/contact-edit drafts survive layout change and app lock | **Partly verified** | Verified 2026-08-23, the security half only. **Nothing writes plaintext form data to disk**: no QML file imports a settings or storage API, and the profile mail renders in is off-the-record.
