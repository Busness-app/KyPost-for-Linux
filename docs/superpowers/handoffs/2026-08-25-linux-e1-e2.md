## E1 — the actual work

Flathub is out (it bans AI software), so GitHub releases are the only Linux
channel, and GitHub releases do not auto-update. Without this, a user who
installs at launch stays on that build indefinitely and never learns otherwise.

This is a **port of a working pattern, not a design**. The server's is
`backend/internal/ghrelease/ghrelease.go`, three functions:

- `Latest(ctx, releasesURL, minAge) (string, error)` — GETs the repo's release
  **list** endpoint and returns the newest tag, skipping releases younger than
  `minAge`.
- `IsNewer(latest, installed) bool` — dotted-numeric compare.
- `parseVersion(v) ([]int, bool)` — refuses anything that is not `N.N.N`.

The server wires it up in `backend/internal/api/server_version.go`: a compiled-in
`serverVersion` constant as the left-hand side, a list endpoint in
`serverReleasesURL`, a cached status struct so opening Settings never issues a
request, and a `minAge` of zero.

Points worth carrying over, each of which exists for a reason the server learned:

1. **Use the list endpoint, not `/releases/latest`.** The list is what lets you
   apply a soak window and skip prereleases.
2. **The installed version must be compiled in**, and it is the *left-hand side*
   of the comparison. `server_version.go:12-28` explains what happens otherwise:
   a binary tagged 1.0.0 whose constant still says 0.1.0 compares itself against
   every release, concludes it is out of date forever, and nags permanently.
   Linux already has the constant — `project(KyPost VERSION 0.2.0)`
   (`CMakeLists.txt:8`) — so plumb *that* through rather than adding a second
   source of truth.
3. **Refuse non-`N.N.N` tags** rather than best-effort parsing them.
4. **Cache the result.** The server polls hourly and serves Settings from cache.
5. **Surface, never act.** The server emails the admin once and shows it in
   Settings. It never touches the host. A flatpak cannot update itself either —
   so this is a notice with a link, not an updater.

The releases URL is `https://api.github.com/repos/Busness-app/KyPost-for-Linux/releases`.
Like the server's, it is compiled in and **permanent for every install it
ships in** — get it right before the first release, not after.

## Bug 1 — WITHDRAWN. This report was wrong.

The original handoff claimed the enrollment code was displayed ungrouped,
citing `app/qml/pages/Settings.qml` binding `PgpEnrollment.verificationCode`
raw.

**That was a false positive.** The QML binding is raw, but the property is
already formatted before it reaches QML: `app/pgp/PgpEnrollmentController.cpp:107`
wraps the derivation in `formatEnrollmentCode`, and that helper
(`core/pgp/DeviceEnrollmentCrypto.cpp:156-162`) groups exactly `4-3-4-3`. It has
been there since `e92b16b`. Linux displays `5R9K-6FW-A18A-8YP`, same as the
browser and Android.

The error was reading the binding and stopping there instead of following the
property to whatever populates it. Recorded rather than deleted so the next
reader does not re-run the same bad inference.

Two items from the original "not verified" list are also now settled and correct:
the bucket is 120 s (`PgpEnrollmentController.cpp:108`), and `transport` is sent
explicitly as `"unifiedpush"` (`core/net/NativeRegistrationClient.cpp:43`).

## Bug 2 — `pin=` is ignored, so the TOFU window stays open

**Good news first: pairing is not broken.** This was the launch plan's open
question, and the answer is definitive. `PairingController.cpp:135-143` parses
with `QUrlQuery` and requires only `sub`, `srv` and `pt` to be present and
non-empty; it reads `reg` optionally and never enumerates or rejects unknown
parameters. An unrecognised `pin=` is silently ignored. **The risk "pairing
breaks for Linux users on day one" is false.**

But Linux never reads the pin, and the pin exists to close a specific hole.
Linux instead captures the SPKI of whatever certificate served registration
(`core/net/NativeRegistrationClient.h:62-70`, `peerSpkiSha256`) and pins later
calls to it via `core/net/CertificatePinSink.cpp:15`. That is trust-on-first-use
— which is honest, and is what the client had before 0.3.0.

The gap: the pairing request is the one call carrying the pairing token, the push
endpoint and the push credentials *together*, and TOFU trusts the certificate
only **after** those are already disclosed. On a network with a locally trusted
CA (enterprise MDM, a user-installed root, a hostile captive portal) an
interceptor reads the token and registers its own device first. The server now
publishes the pin precisely so a client can pin *before* disclosing — Android
honours it, Linux does not.

Per `PLATFORM_BASELINE.md` §1, a client that reads `pin` must **fail closed** on
a mismatch. Linux cannot fail closed on something it never reads. Not
launch-blocking — it is the status quo, and TOFU is the documented fallback — but
it should be a tracked issue rather than an unrecorded difference between
channels.
